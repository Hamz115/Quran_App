# QuranTrack Desktop App — Tauri Implementation Plan

> **Date:** 2026-02-17
> **Status:** Planning
> **Target:** Windows only (initially)

---

## 1. Why Tauri?

QuranTrack's web frontend (React 19 + Vite + Tailwind) maps perfectly to Tauri's model — Tauri wraps a system WebView around your existing frontend, producing a native desktop app with a tiny footprint. Compared to Electron (~150MB+), Tauri ships at ~5-10MB for the shell itself. The existing FastAPI backend gets bundled as a **sidecar** (via PyInstaller), so we don't rewrite any backend code.

**Architecture after Tauri:**
```
┌─────────────────────────────────────────────────┐
│                  Tauri Shell (Rust)              │
│  ┌───────────────────┐  ┌────────────────────┐  │
│  │   WebView2 Window │  │  Sidecar Manager   │  │
│  │  (React Frontend) │  │  (lifecycle ctrl)  │  │
│  └────────┬──────────┘  └────────┬───────────┘  │
│           │                      │               │
│           │   fetch()            │  spawn/kill   │
│           ▼                      ▼               │
│  ┌─────────────────────────────────────────────┐ │
│  │     FastAPI Sidecar (PyInstaller .exe)      │ │
│  │  localhost:8000 — all existing endpoints    │ │
│  │  ┌──────────┐ ┌─────────┐ ┌─────────────┐  │ │
│  │  │ app.db   │ │quran.db │ │ Supabase    │  │ │
│  │  │ (r/w)    │ │ (r/o)   │ │ sync (bg)   │  │ │
│  │  └──────────┘ └─────────┘ └─────────────┘  │ │
│  └─────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────┘
                        +
              Supabase (always syncing)
```

**Key point:** The frontend talks to the sidecar via `fetch("http://localhost:8000/...")` — identical to how it works today. Zero frontend API rewrites.

## 3. Project Structure

Tauri lives **inside `quran_frontend/`** as a `src-tauri/` subfolder. This is the standard Tauri layout for wrapping an existing Vite project.

```
quran_frontend/
├── src/                           # Existing React source (UNCHANGED)
├── public/
│   └── fonts/qpc/                 # 604 QPC fonts (served by WebView, UNCHANGED)
├── dist/                          # Vite build output
├── package.json                   # + @tauri-apps/cli, @tauri-apps/api, @tauri-apps/plugin-shell
├── vite.config.ts                 # UNCHANGED
│
└── src-tauri/                     # NEW — Tauri Rust backend
    ├── tauri.conf.json            # Main Tauri config
    ├── Cargo.toml                 # Rust dependencies
    ├── Cargo.lock                 # Rust lockfile
    ├── build.rs                   # Tauri build script (auto-generated)
    │
    ├── src/
    │   ├── main.rs                # Desktop entry point
    │   └── lib.rs                 # Sidecar lifecycle management
    │
    ├── capabilities/
    │   └── default.json           # Permissions (shell, fs, etc.)
    │
    ├── binaries/                  # PyInstaller sidecar exe goes here
    │   └── quran-backend-x86_64-pc-windows-msvc.exe
    │
    ├── resources/                 # Bundled read-only data files
    │   ├── quran.db               # Read-only Quran database (copied from backend)
    │   └── quran-pages/           # 604 JSON page files (copied from backend)
    │
    └── icons/                     # App icons (auto-generated by tauri init)
        ├── icon.ico
        ├── icon.png
        └── ...
```

**What stays where:**
- **QPC fonts** → stay in `public/fonts/qpc/` — Vite copies them into `dist/`, WebView serves them directly via `@font-face`. No change needed.
- **quran.db + quran-pages/** → copied to `src-tauri/resources/` — bundled as Tauri resources, passed to the sidecar at launch.
- **app.db** → NOT bundled in the exe. Created/managed next to the sidecar exe at runtime (read-write).
- **Frontend code** → completely unchanged. Vite builds to `dist/`, Tauri embeds it.

### 4.5 Rust Sidecar Lifecycle (`src-tauri/src/lib.rs`)

The Rust code needs to:
1. **Spawn** the FastAPI sidecar on app launch
2. **Store** the child process handle
3. **Kill** the sidecar on app close

```rust
use std::sync::Mutex;
use tauri_plugin_shell::ShellExt;
use tauri_plugin_shell::process::CommandChild;

struct SidecarState {
    child: Mutex<Option<CommandChild>>,
}

#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() {
    tauri::Builder::default()
        .plugin(tauri_plugin_shell::init())
        .manage(SidecarState {
            child: Mutex::new(None),
        })
        .setup(|app| {
            // Spawn the FastAPI sidecar on startup
            let sidecar = app.shell()
                .sidecar("binaries/quran-backend")
                .expect("failed to create sidecar command");

            let (mut rx, child) = sidecar
                .spawn()
                .expect("failed to spawn sidecar");

            // Store the child handle for cleanup
            let state = app.state::<SidecarState>();
            *state.child.lock().unwrap() = Some(child);

            // Optionally log sidecar output
            tauri::async_runtime::spawn(async move {
                while let Some(event) = rx.recv().await {
                    match event {
                        tauri_plugin_shell::process::CommandEvent::Stderr(line) => {
                            eprintln!("[backend] {}", String::from_utf8_lossy(&line));
                        }
                        tauri_plugin_shell::process::CommandEvent::Terminated(status) => {
                            eprintln!("[backend] terminated: {:?}", status);
                        }
                        _ => {}
                    }
                }
            });

            Ok(())
        })
        .on_window_event(|window, event| {
            if let tauri::WindowEvent::CloseRequested { .. } = event {
                let state = window.state::<SidecarState>();
                if let Some(child) = state.child.lock().unwrap().take() {
                    let _ = child.kill();
                }
            }
        })
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}
```

## 5. PyInstaller Sidecar (FastAPI Backend)

### 5.1 The Problem: `--onefile` Dual Process

PyInstaller `--onefile` executables spawn two processes: a bootloader parent and the actual Python child. When Tauri calls `child.kill()`, it only kills the bootloader, leaving the Python process orphaned.

**Solution:** Use `--onedir` mode instead (avoids the dual-process issue, faster startup, no temp extraction). The entire output directory becomes the sidecar.

**Alternative if `--onefile` is needed:** Add a parent-process watcher in the Python entrypoint:
```python
import os, threading, time, sys

def watch_parent():
    parent_pid = os.getppid()
    while True:
        try:
            os.kill(parent_pid, 0)  # Check if parent exists
        except OSError:
            os._exit(0)  # Parent died, exit
        time.sleep(1)

if getattr(sys, 'frozen', False):
    threading.Thread(target=watch_parent, daemon=True).start()
```

### 5.2 Entrypoint Script

Create `quran_backend/pyinstaller_entry.py`:
```python
import sys
import os
import multiprocessing

def main():
    multiprocessing.freeze_support()  # Required on Windows

    # Handle --noconsole mode (stdout/stderr are None)
    if getattr(sys, 'frozen', False):
        log_path = os.path.join(os.path.dirname(sys.executable), 'backend.log')
        sys.stdout = open(log_path, 'w', buffering=1)
        sys.stderr = sys.stdout

    import uvicorn
    from main import app

    uvicorn.run(app, host="127.0.0.1", port=8000, workers=1)

if __name__ == "__main__":
    main()
```

**Key details:**
- `multiprocessing.freeze_support()` — required on Windows or the exe spawns infinite child processes
- `workers=1` — uvicorn with `workers > 1` is unreliable in PyInstaller on Windows
- stdout/stderr redirect — `--noconsole` sets them to `None`, causing crashes in uvicorn's logger

### 5.4 Backend Code Changes for PyInstaller

The backend code references file paths using `Path(__file__).parent`. When bundled with PyInstaller, these must resolve to `sys._MEIPASS` for read-only assets and `Path(sys.executable).parent` for read-write files.

**Changes to `quran_backend/main.py` (lines 78-79):**

```python
import sys
from pathlib import Path

# Base path for READ-ONLY bundled assets
if getattr(sys, 'frozen', False) and hasattr(sys, '_MEIPASS'):
    BASE_DIR = Path(sys._MEIPASS)
else:
    BASE_DIR = Path(__file__).parent

# Read-only data
QURAN_DB = BASE_DIR / "quran.db"
QURAN_PAGES_DIR = BASE_DIR / "quran-pages"

# Read-write data (next to the exe when bundled, next to main.py when dev)
if getattr(sys, 'frozen', False):
    WRITABLE_DIR = Path(sys.executable).parent
else:
    WRITABLE_DIR = Path(__file__).parent

APP_DB = WRITABLE_DIR / "app.db"
```

**Also update any other path references in `main.py`** that point to `quran-pages/` or font directories.

## 7. Gotchas & Known Issues

### 7.1 PyInstaller `--onefile` Orphan Process
As described in section 5.1. Use `--onedir` or add a parent-watcher thread. This is the single biggest gotcha.

### 7.2 Windows Defender False Positives
PyInstaller exes are frequently flagged by Windows Defender. Mitigations:
- Code-sign the exe with a certificate
- Submit to Microsoft for whitelisting
- Use `--onedir` mode (less likely to trigger AV)

### 7.3 `--noconsole` + Uvicorn Crash
Uvicorn's logger calls `sys.stdout.isatty()` which crashes when stdout is `None`. Must redirect stdout/stderr before importing uvicorn (handled in the entrypoint script).

### 7.4 Port Conflicts
If port 8000 is already in use, the sidecar will fail to start. Consider:
- Letting the sidecar pick a random free port and communicating it back to the frontend via stdout
- Or using a fixed high port like 18742 that's unlikely to conflict

### 7.5 First Tauri Build is Slow
The first `tauri dev` or `tauri build` downloads and compiles all Rust crates (~2-5 minutes). Subsequent builds are incremental and fast.

### 7.6 Supabase CSP
If the frontend calls Supabase directly (not just via the FastAPI backend), add `https://*.supabase.co` to the CSP `connect-src`.

## 10. Open Questions / Decisions for Later

1. **Port strategy:** Fixed port (8000) vs dynamic free port? Dynamic is safer but requires IPC to tell the frontend which port.
2. **`--onefile` vs `--onedir`:** `--onefile` is cleaner but has the orphan process issue + slow startup. `--onedir` avoids both but is a directory instead of a single exe. Tauri supports both.
3. **Auto-update:** Tauri has a built-in updater plugin. Worth enabling later for distributing updates.
4. **App data location:** Currently `app.db` sits next to the exe. For a proper install, it should go in `%APPDATA%/QuranTrack/`. This is a later refinement.
5. **Code signing:** Required to avoid Windows Defender warnings. Needs a certificate.
6. **Playwright in sidecar:** The backend uses Playwright for PDF export. The bundled exe needs the Playwright driver, though it uses system Edge (`channel="msedge"`) so browser binaries aren't needed. Needs testing.
